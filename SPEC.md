## 1. Общая концепция

House Studio — игра, в которой пользователь получает пустой участок земли и самостоятельно
проектирует дом, строит помещения, устанавливает двери и окна, выбирает отделочные материалы,
расставляет мебель и занимается ландшафтным дизайном.

В отличие от симуляторов жизни, основной продукт — именно строительный редактор.

Игра должна сочетать три ключевых качества:

1. Простое и интуитивное строительство, без необходимости владеть профессиональными CAD-программами.
2. Визуально привлекательную 3D-графику с реалистичными материалами, освещением и архитектурными объектами.
3. Гибкую техническую архитектуру, допускающую постепенное расширение функциональности.

Пользователь должен иметь возможность начать с пустого участка, построить дом, оформить
территорию, сохранить работу и вернуться к редактированию.

### 1.1. Основной игровой цикл

1. Пустой участок — выбор или создание проекта.
2. Проектирование — стены, комнаты, полы, этажи.
3. Архитектура — двери, окна, крыша, фасады.
4. Интерьер — мебель, отделка, декор, освещение.
5. Ландшафт — дорожки, растения, заборы, территория.
6. Результат — просмотр, сохранение, продолжение строительства.

### 1.2. Границы проекта

Необходимо сразу разделить конечную концепцию и первую рабочую версию.

Конечная концепция включает многоэтажные дома, сложные крыши, реалистичную мебель, полноценный
ландшафт, освещение, большую библиотеку материалов и продвинутый редактор.

Первая рабочая версия (MVP) должна содержать только базовые системы, но уже позволять построить
простое здание и сохранить его.

Не следует пытаться реализовать все возможности inZOI сразу. Особенно важно не жертвовать
устойчивостью строительства ради декоративных визуальных эффектов.

## 3. Архитектура программного обеспечения

Рекомендуемая архитектура — модульный монолит.

Это означает, что приложение представляет собой один проект, но его внутренние системы
логически независимы. Не следует создавать микросервисную инфраструктуру для MVP.

### 3.1. Схема компонентов

```
┌───────────────────────────────────────────────────────────┐
│ PRESENTATION LAYER                                         │
│ React UI • инструменты • панели • каталог                  │
└───────────────────────────┬─────────────────────────────────┘
                             │ вызывает команды / читает store
┌───────────────────────────▼─────────────────────────────────┐
│ APPLICATION LAYER                                           │
│ состояние • команды • история • режимы редактора            │
└───────────────────────────┬─────────────────────────────────┘
                             │ читает/изменяет доменные данные
┌───────────────────────────▼─────────────────────────────────┐
│ DOMAIN LAYER                                                 │
│ геометрия • стены • комнаты • объекты • ограничения          │
└───────────────────────────┬─────────────────────────────────┘
              ┌──────────────┴───────────────┐
              │ подписка на изменения проекта │
┌─────────────▼─────────────┐   ┌─────────────▼─────────────┐
│ RENDERING                 │   │ PERSISTENCE                │
│ Three.js • WebGL          │   │ IndexedDB • JSON • импорт   │
└────────────────────────────┘   └─────────────────────────────┘
```

Presentation никогда не обращается к Domain или Rendering напрямую — только через
Application (store и команды). Rendering и Persistence оба являются «читателями» состояния
проекта из Application и не содержат собственной бизнес-логики.

#### Слой 1. Presentation

Отвечает только за отображение интерфейса и получение действий пользователя.

Примеры компонентов:

- `BuildToolbar` — панель строительства.
- `ObjectCatalog` — каталог мебели и объектов.
- `InspectorPanel` — свойства выделенного объекта.
- `ProjectMenu` — создание, сохранение и загрузка.
- `NotificationSystem` — ошибки и уведомления.

Компоненты интерфейса не должны напрямую изменять меши Three.js. Вместо этого они вызывают
команды игрового редактора.

#### Слой 2. Application

Центральная логика приложения. Отвечает за:

- Управление активным инструментом.
- Состояние выделения.
- Выполнение команд.
- Отмену и повтор операций.
- Управление текущим проектом.
- Передачу данных в визуализацию и сохранение.

#### Слой 3. Domain

Содержит правила строительства. Например:

- Стена не может иметь нулевую длину.
- Дверь должна находиться внутри допустимого участка стены.
- Объект нельзя поставить за пределами участка.
- Стены должны корректно привязываться к строительной сетке.
- Перемещение объекта должно учитывать ограничения размещения.

Этот слой должен работать без React и Three.js. Геометрические расчёты необходимо
реализовать в виде обычных TypeScript-функций, которые можно тестировать отдельно.

#### Слой 4. Rendering

Преобразует состояние проекта в 3D-сцену. Например:

*(реконструировано)*

```tsx
// Rendering читает данные проекта из store и строит декларативную сцену.
// Он не хранит собственного состояния геометрии — только производные меши.

function WallsLayer() {
  const walls = useProjectStore((s) => s.project.entities.walls);
  return (
    <group name="walls">
      {Object.values(walls).map((wall) => (
        <WallMesh key={wall.id} wall={wall} />
      ))}
    </group>
  );
}

function WallMesh({ wall }: { wall: Wall }) {
  const material = useMaterial(wall.materialId);
  const { position, rotationY, length } = wallTransform(wall); // domain-функция
  return (
    <mesh position={position} rotation={[0, rotationY, 0]} castShadow receiveShadow>
      <boxGeometry args={[length, wall.height, wall.thickness]} />
      <primitive object={material} attach="material" />
    </mesh>
  );
}
```

3D-сцена — отображение данных проекта, а не единственный источник этих данных.

Это принципиально важно: сохранение дома не должно зависеть от сериализации готовой
Three.js-сцены.

#### Слой 5. Persistence

Отвечает за работу с файлами и локальным хранилищем. Модуль не должен содержать логики
камеры, строительства или интерфейса.

## 5. Модель строительного мира

Это одна из важнейших систем всего проекта. Следует использовать единую метрическую систему
координат.

### 5.1. Координаты

В Three.js принять:

- X — горизонтальная ось.
- Y — высота.
- Z — горизонтальная ось.

Одна единица сцены равна одному метру. Плоскость участка располагается по XZ. Высота
рассчитывается по Y.

| Параметр | Значение |
|---|---|
| Размер участка, м | 40 × 40 |
| Шаг сетки, м | 0,5 |
| Высота стен, м | 2,8 |

Параметры должны храниться в конфигурации (`src/config`), а не быть разбросаны по исходному коду.

### 5.2. Привязка к сетке

Все основные строительные операции привязываются к единой координатной сетке.

Алгоритм *(реконструировано)*:

```
function snapToGrid(point, gridStep):
    x = round(point.x / gridStep) * gridStep
    z = round(point.z / gridStep) * gridStep
    return { x, z }

function snapToExistingGeometry(point, candidates, tolerance):
    for each candidate in candidates:
        if distance(point, candidate.endpoint) <= tolerance:
            return candidate.endpoint   # приоритет над сеткой
    return null

function resolveSnapPoint(rawPoint, context):
    geometrySnap = snapToExistingGeometry(rawPoint, context.wallEndpoints, context.snapTolerance)
    if geometrySnap is not null:
        return geometrySnap
    return snapToGrid(rawPoint, context.gridStep)
```

Для стен, комнат и дверей должны быть предусмотрены правила привязки к существующей геометрии.

Например, конец новой стены должен автоматически совпадать с началом существующей стены,
если курсор находится достаточно близко к ней.

Важный момент: привязка должна производиться в доменной логике. Визуальная сетка лишь
отображает её.

### 5.3. Единая система уровней

Даже если MVP поддерживает только один этаж, в структуре данных необходимо предусмотреть
этажи сразу. Каждый строительный объект должен иметь ссылку на уровень.

Пример *(реконструировано)*:

```ts
interface Level {
  id: string;
  index: number;        // 0 = первый этаж
  name: string;         // "Этаж 1"
  elevation: number;    // высота чистого пола в мировых координатах (м)
  height: number;       // высота этажа от пола до пола следующего уровня (м)
  visible: boolean;     // видимость при редактировании других этажей
}

interface LevelReference {
  levelId: string;
}

// Любая строительная сущность обязана ссылаться на уровень:
interface Wall extends LevelReference { /* ... */ }
```

`elevation` — высота чистого пола соответствующего этажа в мировых координатах.

Это позволит добавить второй и последующие этажи без полной переработки существующих зданий.

## 6. Структура данных проекта

Необходимо создать единый формат проекта House Studio.

Основной принцип: **проект хранит геометрические и логические данные, а не готовые 3D-меши.**

### 6.1. Основные типы

*(реконструировано)*

```ts
type EntityId = string;

interface Vec2 { x: number; z: number; }

interface ProjectMeta {
  id: string;
  name: string;
  createdAt: string;    // ISO-дата
  updatedAt: string;
  formatVersion: string; // semver формата сохранения, см. раздел 16.3
}

interface Project {
  meta: ProjectMeta;
  siteSize: { width: number; depth: number };
  levels: Record<EntityId, Level>;
  entities: {
    walls: Record<EntityId, Wall>;
    floors: Record<EntityId, Floor>;
    openings: Record<EntityId, Opening>;
    items: Record<EntityId, PlacedItem>;
    roofs: Record<EntityId, Roof>;
    landscape: Record<EntityId, LandscapeEntity>;
  };
}

type ProjectEntity = Wall | Floor | Opening | PlacedItem | Roof | LandscapeEntity;
```

Следует реализовать отдельные типы для стен, полов, предметов, дверей, окон и объектов
территории.

### 6.2. Стены

*(реконструировано)*

```ts
interface Wall extends LevelReference {
  id: EntityId;
  start: Vec2;
  end: Vec2;
  height: number;        // м, по умолчанию из конфигурации
  thickness: number;     // м
  materialId: {
    exterior: string;
    interior: string;
  };
  openingIds: EntityId[]; // ссылки на двери/окна, принадлежащие этой стене
}
```

Стена хранится как параметрический объект. Это даёт возможность изменять её длину, высоту,
толщину и материалы без ручного редактирования вершин меша.

### 6.3. Проёмы

*(реконструировано)*

```ts
type OpeningKind = "door" | "window";

interface Opening extends LevelReference {
  id: EntityId;
  wallId: EntityId;
  kind: OpeningKind;
  offset: number;        // от начала стены до левого края проёма, м
  width: number;
  height: number;
  sillHeight: number;    // высота подоконника (0 для дверей)
  assetId: string;       // ссылка на каталог моделей двери/окна
}
```

`offset` — расстояние от начала стены до левого края проёма вдоль направления стены.

Проёмы принадлежат конкретной стене. При перемещении стены нужно сохранять связь с
установленными дверями и окнами.

Перед изменением длины стены необходимо проверять, помещаются ли в неё существующие проёмы.

### 6.4. Полы

*(реконструировано)*

```ts
interface Floor extends LevelReference {
  id: EntityId;
  polygon: Vec2[];        // вершины многоугольника, минимум 3 точки
  materialId: string;
  thickness: number;      // м
}
```

Пол описывается двумерным многоугольником, по которому создаётся 3D-геометрия.

В первой версии редактор может поддерживать только прямоугольные полы, но хранить их
следует в виде многоугольников.

### 6.5. Размещаемые предметы

*(реконструировано)*

```ts
interface PlacedItem extends LevelReference {
  id: EntityId;
  assetId: string;        // ссылка на каталог мебели/декора
  position: { x: number; y: number; z: number };
  rotationY: number;      // радианы
  scale?: number;         // допускается только если разрешено ассетом
  materialVariantId?: string;
}
```

`assetId` ссылается на каталог моделей. Саму 3D-модель не нужно дублировать в каждом
объекте проекта.

Впоследствии эту схему можно расширить свойствами цвета, варианта обивки, освещения и
другими параметрами. Для MVP можно использовать одни и те же объекты с несколькими
вариантами материалов.

### 6.6. Полная структура проекта

*(реконструировано — сводная версия раздела 6.1 с версионированием и правилами округления)*

```ts
const COORDINATE_PRECISION = 3; // знаков после запятой при сохранении, чтобы исключить
                                  // накопление ошибок float при многократной привязке к сетке

interface ProjectFile {
  formatVersion: string;  // например "1.0.0"
  project: Project;
}
```

`ProjectEntity` — объединение всех допустимых типов объектов.

Формат должен поддерживать версионирование. Если в будущем структура изменится, старые
проекты нужно обновлять через миграции.

Следует определить единые правила округления координат и проверки корректности геометрии.
Это исключит накопление ошибок при многократной привязке объектов к сетке.

## 7. Система строительства стен

Система строительства стен должна быть независима от пользовательского интерфейса и
рендеринга.

### 7.1. Пользовательский сценарий

1. Игрок выбирает инструмент «Стена».
2. Наводит курсор на участок.
3. Появляется точка начала строительства.
4. Игрок нажимает левую кнопку мыши.
5. При перемещении курсора отображается предварительная стена.
6. Игрок нажимает повторно, фиксируя конечную точку.
7. Стена добавляется в проект одной командой.

До подтверждения объект должен существовать только как визуальный предпросмотр. Не следует
записывать его в постоянное состояние проекта на каждом движении мыши.

### 7.2. Геометрия стен

В MVP достаточно генерировать стены из `BoxGeometry`.

Исходные параметры *(реконструировано)*:

```ts
interface WallGeometryParams {
  length: number;     // |end - start|
  height: number;
  thickness: number;
  angle: number;      // радианы, направление от start к end относительно оси X
}
```

Создаётся параллелепипед длиной `length`, высотой `height` и толщиной `thickness`. Его
горизонтальный центр устанавливается в середине отрезка, вертикальный центр — на половине
высоты над уровнем пола. Стена поворачивается на угол `angle` относительно оси Y.

При этом необходимо один раз зафиксировать локальную ориентацию геометрии, чтобы направление
поворота соответствовало осям Three.js.

#### Соединение стен

В первой версии возможны небольшие пересечения геометрии в углах.

В следующем этапе необходимо создать систему соединений, которая корректно обрабатывает
L-, T- и X-образные стыки стен.

Для этого рекомендуется нормализовать точки соединения и затем перейти к отдельной
топологической модели стен.

Не нужно создавать сложный геометрический движок соединений до появления надёжного базового
редактора.

### 7.3. Построение комнат

Отдельный инструмент «Комната» должен позволять построить прямоугольную комнату двумя кликами.

Алгоритм *(реконструировано)*:

```
function createRectangularRoom(cornerA, cornerB, level):
    p1, p2, p3, p4 = rectangleCorners(cornerA, cornerB)   # по часовой стрелке
    wallA = createWall(p1, p2, level)
    wallB = createWall(p2, p3, level)
    wallC = createWall(p3, p4, level)
    wallD = createWall(p4, p1, level)
    floor = createFloor(polygon=[p1, p2, p3, p4], level)
    return CreateRoomCommand(walls=[wallA, wallB, wallC, wallD], floor=floor)
```

Все пять объектов должны создаваться атомарно: либо успешно создаётся вся комната, либо
операция отменяется.

На первом этапе не требуется автоматически распознавать любое замкнутое пространство как
комнату. Для произвольных помещений впоследствии понадобится топологический граф стен и
алгоритм поиска замкнутых контуров.

## 8. Двери, окна и проёмы

Эта система должна разрабатываться после базового редактора стен, но её архитектуру
необходимо предусмотреть заранее.

Необходимо реализовать инструмент размещения дверей и окон, который работает исключительно
с существующими стенами.

При наведении курсора на стену показывается место установки. После клика проём записывается
в данные стены, а геометрия стены пересоздаётся.

### 8.1. Генерация отверстий

Для базовых прямоугольных проёмов не рекомендуется сразу использовать универсальные
CSG-операции.

Более предсказуемый подход — процедурно разделять стену на участки:

- Слева от проёма.
- Справа от проёма.
- Над проёмом.
- Под проёмом, если это окно.

Для нескольких проёмов понадобится разбить длину стены по их горизонтальным границам и
сформировать непересекающиеся участки геометрии.

Это даст более контролируемую производительность и позволит точно валидировать проёмы.

CSG можно рассматривать позже, когда понадобятся арки и нестандартные вырезы.

### 8.2. Ограничения

Система должна проверять, что:

- Проём помещается внутри стены.
- Проёмы не пересекаются.
- Верхняя граница не превышает высоту стены.
- Высота подоконника неотрицательна.
- Двери корректно совмещены с уровнем чистого пола.

При удалении стены необходимо удалять и связанные с ней проёмы либо явно обрабатывать их в
рамках одной операции.

## 9. Система этажей и крыш

Эти возможности относятся к этапам после MVP, однако данные должны быть готовы к их
внедрению.

### Этажи

Для каждого уровня используется собственная высота и отдельная группа объектов.

Необходимые будущие возможности:

- Добавление этажа.
- Копирование планировки предыдущего этажа.
- Скрытие верхних этажей.
- Переключение активного уровня.
- Редактирование высоты уровня.
- Размещение лестниц.

Инструменты строительства должны работать только с активным этажом, если пользователь явно
не выбрал другой режим.

### Крыши

Для крыш требуется отдельная параметрическая система.

*(реконструировано)*

```ts
type RoofType = "flat" | "gable" | "hip" | "combined";

interface Roof extends LevelReference {
  id: EntityId;
  type: RoofType;
  footprint: Vec2[];   // контур здания/секции, над которой строится крыша
  pitch: number;        // угол ската в градусах (0 для flat)
  overhang: number;     // свес карниза, м
  ridgeHeight?: number; // для gable/hip — высота конька над footprint
  materialId: string;
}
```

Приоритет реализации:

1. Плоские крыши.
2. Двускатные крыши.
3. Вальмовые крыши.
4. Сложные комбинированные крыши.

Крыши не следует автоматически генерировать по произвольной форме здания на ранней стадии.
Сначала необходимо реализовать создание крыши над прямоугольным контуром.

## 10. Система размещения объектов

Каталог объектов должен работать как универсальная система.

К мебели, растениям и декоративным предметам применяется единая механика размещения.
Различия задаются параметрами конкретного объекта.

### 10.1. Каталог

Каждый объект должен иметь описание.

*(реконструировано)*

```ts
type PlacementSurface = "floor" | "wall" | "ceiling" | "terrain";

interface CatalogItem {
  assetId: string;
  name: string;
  category: "furniture" | "decor" | "plant" | "landscape" | "door" | "window";
  placementSurface: PlacementSurface;
  footprint: { width: number; depth: number; height: number }; // для коллизий, м
  anchor: "center" | "base-center";  // точка привязки модели
  scalable: boolean;
  materialVariants: string[]; // допустимые materialVariantId
  modelUrl?: string;          // путь к GLB, отсутствует для процедурных заглушек
}
```

В первой версии допустимо использовать процедурные геометрические заглушки вместо
полноценных GLB-моделей. Например, диван может временно состоять из нескольких
параллелепипедов.

Важно сразу отделить модель предмета от его данных.

### 10.2. Механика размещения

После выбора предмета:

1. Появляется полупрозрачная модель.
2. Она перемещается за курсором.
3. Позиция рассчитывается через пересечение луча с поверхностью размещения.
4. Проводится проверка допустимости размещения.
5. После клика создаётся постоянный объект.

На первом этапе можно ограничиться размещением предметов на горизонтальной плоскости.
Позднее добавить привязку к стенам, столешницам и другим поверхностям.

### 10.3. Трансформации

Для размещённых объектов реализовать:

| Действие | Поведение |
|---|---|
| Перемещение | Перетаскивание мышью |
| Поворот | Клавиши Q / E или числовое поле |
| Масштабирование | Только если разрешено объектом |
| Удаление | Delete |
| Дублирование | Ctrl + D |
| Выделение | Левый клик |

Для первого MVP обязательны размещение, выделение, перемещение, поворот и удаление.
Дублирование и масштабирование допускаются в следующем этапе.

### 10.4. Проверка коллизий

Система должна использовать упрощённые ограничивающие объёмы для обнаружения пересечений.

В первом прототипе можно реализовать AABB или простые ориентированные прямоугольники для
объектов мебели.

Нужно различать:

- Предупреждение о пересечении.
- Запрет выхода за границы участка.
- Разрешённые пересечения декоративных объектов.

Не следует использовать полноценный физический движок исключительно ради расстановки мебели.
При появлении режима прогулки физику персонажа можно подключить отдельно.

## 11. Ландшафтный редактор

Участок должен восприниматься как полноценная часть игры, а не просто плоскость под зданием.

### 11.1. MVP территории

На первом этапе реализовать:

- Земельный участок 40 × 40 метров.
- Зелёное покрытие земли.
- Возможность размещения деревьев.
- Возможность размещения декоративных объектов.
- Прямые дорожки.
- Границы участка.

Территория должна редактироваться тем же механизмом выбора и размещения объектов, что и
интерьер.

### 11.2. Дорожки

Использовать отдельный параметрический объект.

*(реконструировано)*

```ts
interface LandscapeEntity extends LevelReference {
  id: EntityId;
  kind: "path" | "fence" | "plant" | "decor";
}

interface Path extends LandscapeEntity {
  kind: "path";
  segments: Vec2[];   // минимум 2 точки; MVP — ровно 2 (один прямой сегмент)
  width: number;       // м
  materialId: string;
}
```

В MVP достаточно дорожки из одного прямого сегмента. Затем можно добавить ломаные и
криволинейные дорожки.

### 11.3. Редактор рельефа

В следующем этапе следует предусмотреть:

- Подъём и опускание земли.
- Сглаживание.
- Покраску территории.
- Настройку размера кисти.
- Настройку силы воздействия.

Подходящая основа — heightmap с регулярной сеткой вершин.

Однако редактирование рельефа создаёт дополнительные вопросы для фундаментов, дорожек и
объектов.

Поэтому в MVP поверхность участка должна оставаться плоской.

Рельеф необходимо вынести в самостоятельный модуль и не смешивать с логикой стен.

## 12. 3D-движок и визуализация

Реалистичная графика — важная особенность House Studio, но визуальные эффекты не должны
мешать редактированию.

### 12.1. Структура сцены

*(реконструировано)*

```
Scene
├── Lighting            # направленный свет, заполняющий свет, окружение
├── Ground               # плоскость участка + текстура травы
├── EditorGrid            # вспомогательная сетка (не сохраняется в проект)
├── BuildingLayers
│   ├── WallsLayer
│   ├── FloorsLayer
│   ├── OpeningsLayer      # проёмы влияют на геометрию WallsLayer, но помечаются отдельно
│   └── RoofsLayer
├── FurnitureLayer
├── LandscapeLayer
├── EditorHelpers          # предпросмотр, подсветка выделения, измерения
└── CameraRig
```

Следует разделить игровые объекты и вспомогательные элементы редактора.

Сетка, линии измерений и подсветка выделения не должны попадать в сохраняемый проект как
строительные сущности.

### 12.2. Материалы

Использовать физически обоснованную модель материалов PBR.

Базовый вариант — `MeshStandardMaterial`.

Для реалистичной отделки понадобятся:

- Base Color.
- Roughness.
- Metalness.
- Normal Map.
- Ambient Occlusion, если доступна.
- Корректный масштаб UV-текстур.

Материалы должны храниться в отдельном каталоге и иметь стабильные идентификаторы.

Пример *(реконструировано)*:

```ts
interface MaterialDefinition {
  id: string;                 // например "wall-plaster-white"
  name: string;
  category: "wall" | "floor" | "roof" | "landscape";
  baseColorMapUrl: string;
  normalMapUrl?: string;
  roughnessMapUrl?: string;
  aoMapUrl?: string;
  roughness: number;          // 0..1, используется если карты нет
  metalness: number;          // 0..1
  uvScale: { u: number; v: number };
}
```

В перспективе нужны отдельные параметры для масштаба и поворота текстуры.

### 12.3. Освещение

На начальном этапе:

- Направленный солнечный свет.
- Мягкий заполняющий свет.
- Тени от зданий и деревьев.
- Нейтральное окружение.
- Корректное цветовое пространство.
- Настройка экспозиции и tone mapping.

Рекомендуется начать с мягких теней и PBR-материалов, не подключая сразу тяжёлые
постэффекты.

Во время разработки необходимо обеспечить переключение между качеством графики и
производительностью.

### 12.4. Графические пресеты

Предусмотреть три профиля:

| Настройка | Low | Medium | High |
|---|---|---|---|
| Разрешение рендера | Пониженное | Стандартное | Повышенное |
| Тени | Упрощённые | Средние | Высокие |
| Детализация | Низкая | Средняя | Высокая |
| Постобработка | Выключена | Ограниченная | Расширенная |

На первых этапах достаточно одного рабочего профиля и переключателя теней.

Необходимо учитывать, что браузерный Three.js не обеспечивает автоматически уровень графики
inZOI. Для приближения к этому качеству потребуются хорошие модели, текстуры, освещение,
оптимизация и полноценный художественный пайплайн.

## 13. Камера и управление

В игре должны быть три основных режима камеры.

| Режим | Этап | Описание |
|---|---|---|
| Режим строительства | MVP | Изометрический вид с возможностью вращения, приближения и перемещения |
| Вид сверху | Следующий этап | Ортографическая камера, удобная для построения плана здания |
| Режим прогулки | Позднее | Осмотр помещений от первого лица без возможности строить |

### 13.1. Управление камерой в MVP

| Действие | Управление |
|---|---|
| Вращение | Правая кнопка мыши + движение |
| Перемещение | Средняя кнопка мыши + движение |
| Приближение | Колесо мыши |
| Выделение | Левая кнопка мыши |
| Действие инструмента | Левая кнопка мыши |
| Отмена инструмента | Esc |

Нужно исключить конфликт между действиями камеры и строительными инструментами.

Во время строительства стен левая кнопка мыши должна работать только с редактором, а не
вращать камеру.

При наведении на интерфейс действия должны обрабатываться интерфейсом и не передаваться
3D-сцене.

Для определения позиции курсора использовать raycasting.

Для строительства на плоском участке луч должен пересекать математическую плоскость
текущего уровня, а не обязательно видимую сетку.

Это сделает размещение независимым от текстур и вспомогательной графики.

## 14. Архитектура инструментов редактора

Необходимо реализовать расширяемую систему инструментов.

Нельзя допускать, чтобы логика всех режимов находилась в одном компоненте `App.tsx`.

### 14.1. Интерфейс инструмента

Пример архитектурного контракта *(реконструировано)*:

```ts
interface EditorToolContext {
  project: Project;
  activeLevelId: string;
  raycast: () => Vec2 | null;      // пересечение луча с плоскостью текущего уровня
  snap: (point: Vec2) => Vec2;      // domain snapping
  dispatch: (command: Command) => void;
  cancelPreview: () => void;
}

interface EditorTool {
  id: string;
  onPointerDown(ctx: EditorToolContext): void;
  onPointerMove(ctx: EditorToolContext): void;
  onPointerUp(ctx: EditorToolContext): void;
  onKeyDown(ctx: EditorToolContext, key: string): void;
  onActivate(ctx: EditorToolContext): void;
  onDeactivate(ctx: EditorToolContext): void;
  getPreview(): PreviewGeometry | null; // визуальный предпросмотр, не часть проекта
}
```

Это проектный интерфейс; конкретные типы контекстов необходимо определить при реализации.

Каждый инструмент должен получать доступ к необходимым сервисам через контекст или
конструктор, а не напрямую импортировать весь глобальный store.

### 14.2. Режимы инструментов

Пример состояний инструмента строительства стен *(реконструировано)*:

```ts
type WallToolState =
  | { phase: "idle" }
  | { phase: "awaiting-start" }
  | { phase: "drawing"; start: Vec2; cursor: Vec2 }
  | { phase: "confirming"; start: Vec2; end: Vec2 };
```

Система должна корректно обрабатывать нажатие Esc на любом промежуточном этапе.

Отмена предварительного размещения не должна добавлять команду в историю действий.

### 14.3. Подсветка

В редакторе должны быть отдельные визуальные состояния:

- Выделенный объект.
- Объект под курсором.
- Предварительное размещение.
- Некорректное размещение.

Рекомендуется использовать бирюзовую подсветку для выделения и красную для недопустимой
позиции.

Подсветка не должна изменять постоянный материал строительного объекта.

## 15. Система истории действий

Undo/Redo необходимо реализовать с самого начала.

Если добавить эту функцию поздно, придётся переписывать многие инструменты.

### 15.1. Принцип Command Pattern

Каждое изменение проекта должно быть атомарной операцией.

Примеры *(реконструировано)*:

```ts
interface Command {
  id: string;
  label: string;       // для отладки/истории, например "Добавить стену"
  apply(project: Project): Project;
  invert(project: Project): Project;
}

class AddWallCommand implements Command {
  id = crypto.randomUUID();
  label = "Добавить стену";
  constructor(private wall: Wall) {}
  apply(project: Project): Project {
    return produce(project, (draft) => {
      draft.entities.walls[this.wall.id] = this.wall;
    });
  }
  invert(project: Project): Project {
    return produce(project, (draft) => {
      delete draft.entities.walls[this.wall.id];
    });
  }
}

class CreateRoomCommand implements Command {
  // объединяет 4 стены + пол в одну атомарную команду, см. раздел 7.3
}

class MoveItemCommand implements Command {
  // одно перетаскивание мышью = одна запись в истории, см. раздел 15.2
}
```

Операция изменения данных выполняется через единый `CommandManager`.

Предпочтительная реализация — Immer patches и inverse patches с централизованным
применением.

При этом все изменения должны происходить только в данных проекта, а не в Three.js-мешах.

### 15.2. Требования к истории

- Ctrl + Z отменяет последнее действие.
- Ctrl + Shift + Z возвращает отменённое действие.
- После нового действия ветка Redo очищается.
- История ограничена, например, 100 операциями.
- Одна комната считается одной операцией.
- Перемещение предмета за один жест считается одной операцией.

Движение курсора и обновление предпросмотра не должны создавать сотни записей в истории.

Историю можно хранить только в текущей сессии. При перезапуске достаточно восстановить
сохранённое состояние проекта.

## 16. Хранение и сохранение

Сохранение должно работать до внедрения облачной инфраструктуры.

### 16.1. IndexedDB

Основное хранилище браузерной версии — IndexedDB.

Использовать его для хранения проектов и настроек приложения.

Для первой версии не нужно размещать бинарные модели и текстуры внутри каждого проекта:
они должны загружаться из общего каталога ассетов.

### 16.2. Автосохранение

Автосохранение должно запускаться после подтверждённых изменений.

Рекомендуемая логика *(реконструировано)*:

```
on(commandApplied):
    markDirty()
    debounce(1500ms):
        setStatus("saving")
        try:
            writeProjectToIndexedDb(project)
            setStatus("saved")
        catch (error):
            setStatus("error", error)
```

При частых изменениях использовать debounce.

Сохранение не должно запускаться на каждый кадр или движение мыши.

Запись должна быть транзакционной, а интерфейс должен различать состояния «Сохранение»,
«Сохранено» и «Ошибка сохранения».

### 16.3. Экспорт и импорт

Реализовать экспорт проекта в JSON.

*(реконструировано)*

```ts
function exportProjectToJson(project: Project): string {
  const file: ProjectFile = { formatVersion: CURRENT_FORMAT_VERSION, project };
  return JSON.stringify(file, null, 2);
}

function importProjectFromJson(raw: string): Project {
  const parsed = JSON.parse(raw);
  const file = ProjectFileSchema.parse(parsed); // Zod-валидация, см. ниже
  return migrateProjectFile(file).project;
}
```

Импортируемый файл должен проверяться через схему данных до загрузки в редактор.

Необходимо предусмотреть:

- Проверку версии формата.
- Проверку обязательных полей.
- Проверку размеров участка.
- Проверку геометрических значений.
- Обработку неизвестных идентификаторов ассетов.
- Сообщение об ошибке без разрушения текущего проекта.

Некорректный импорт не должен удалять текущую работу пользователя.

Схему миграции необходимо добавить до первого изменения структуры сохранённых данных.

## 17. Пользовательский интерфейс

Интерфейс должен выглядеть как современный архитектурный редактор, но оставаться понятным
обычному игроку.

Рекомендуемый стиль: светлые поверхности, графитовые панели, нейтральная типографика,
умеренные бирюзовые акценты.

Не следует копировать оформление The Sims 4 или inZOI буквально.

### 17.1. Компоновка экрана

Верхняя панель — название игры/проекта, статус сохранения. Слева — вертикальная панель
инструментов. Основная область — 3D-вьюпорт с сеткой и индикатором активного режима. Справа —
инспектор свойств выделенного объекта. Снизу — контекстный каталог, который меняет
содержимое в зависимости от активного инструмента.

### 17.2. Верхняя панель

Содержит название игры, название проекта, создание и открытие проекта, импорт, экспорт,
сохранение, Undo и Redo.

Также отображает индикатор состояния сохранения.

### 17.3. Левая панель

Вертикальная панель основных инструментов:

- Выделение.
- Стены.
- Комнаты.
- Полы.
- Двери и окна.
- Мебель.
- Ландшафт.
- Материалы.
- Удаление.

Недоступные функции должны быть скрыты или явно помечены как недоступные, но не выглядеть
рабочими.

### 17.4. Правая панель

Инспектор выбранного объекта.

Для стены отображаются длина, высота, толщина, материалы и удаление.

Для мебели — позиция, поворот, размеры и доступные варианты материалов.

При отсутствии выделения можно показывать свойства участка или краткую инструкцию по
активному инструменту.

### 17.5. Нижняя панель

Контекстный каталог.

При выборе мебели отображаются категории мебели, при выборе материалов — доступная отделка,
при выборе строительства — типы строительных элементов.

Таким образом, одна панель используется для разных инструментов.

### 17.6. Адаптивность

Первую версию необходимо ориентировать на экраны компьютеров с разрешением от 1280 × 720.

На небольших экранах панели могут сворачиваться. Однако полноценное сенсорное управление и
мобильный интерфейс не входят в MVP.

## 18. Производительность и оптимизация

Браузерная игра должна сохранять отзывчивость во время редактирования.

### Целевые показатели

| Параметр | Цель |
|---|---|
| Частота кадров | 60 FPS на подходящем настольном оборудовании |
| Минимально комфортная частота | Около 30 FPS |
| Размер участка MVP | 40 × 40 м |
| Объём тестового проекта | 100 стен и 200 объектов |
| Время реакции предпросмотра | Без ощутимой задержки ввода |

Эти значения — цели для измерения, а не гарантированные характеристики. Их необходимо
проверять на конкретном оборудовании.

### Основные меры оптимизации

1. **Переиспользование геометрии.** Одинаковые предметы должны иметь общие ресурсы
   геометрии и материалов там, где это допустимо.
2. **InstancedMesh.** Подходит для повторяющихся деревьев, декоративных элементов и
   одинаковых предметов. Не следует использовать его для всех объектов без учёта
   индивидуального выделения и редактирования.
3. **Контроль изменений сцены.** Изменение одной стены не должно пересоздавать весь дом.
4. **Кэширование.** Загруженные модели и текстуры нужно переиспользовать.
5. **Уровни детализации.** Добавить после появления большого количества высокополигональных
   объектов.
6. **Контроль разрешения.** Использовать ограниченный device pixel ratio и адаптивные
   настройки качества.
7. **Асинхронная загрузка.** Тяжёлые модели не должны блокировать весь редактор.

На первом этапе оптимизация должна быть измеряемой. Не нужно заранее внедрять сложный ECS
или собственный низкоуровневый движок.

## 19. Система ассетов

Для качественной графики в будущем понадобится отдельная библиотека объектов.

Рекомендуемый формат 3D-моделей — GLB/glTF.

Необходимо стандартизировать:

- Единицы измерения: метры.
- Вертикальную ось: Y.
- Точку привязки предмета.
- Корректную ориентацию.
- Названия материалов.
- Размеры объекта.
- Идентификатор ассета.

Для напольной мебели удобно располагать точку привязки по центру основания.

Для настенных объектов понадобится отдельная ориентация точки крепления.

Текстуры и модели должны быть лицензированы для использования в проекте. Не следует
извлекать модели, интерфейс или текстуры непосредственно из The Sims 4 или inZOI.

На этапе MVP лучше использовать процедурные объекты, чем подключать случайные модели с
разными размерами и системами координат.

Впоследствии можно организовать процесс *(реконструировано)*:

1. Отбор референсов и требований к объекту (размеры, категория, точка привязки).
2. Моделирование или лицензированная закупка модели в GLB.
3. Проверка масштаба, ориентации и origin по чек-листу выше.
4. Оптимизация полигонажа и текстур под целевые графические пресеты (раздел 12.4).
5. Регистрация объекта в каталоге (`CatalogItem`, раздел 10.1) с уникальным `assetId`.
6. Ручная проверка размещения в редакторе перед публикацией в общий каталог.

## 20. Качество, тестирование и безопасность

Необходимо разделить тестирование геометрической логики и проверку пользовательских
сценариев.

### 20.1. Модульные тесты

Использовать Vitest.

Проверять:

- Привязку координат к сетке.
- Расчёт длины стены.
- Углы поворота стен.
- Определение пересечений отрезков.
- Ограничение объектов границами участка.
- Проверку допустимости размеров.
- Корректность создания прямоугольной комнаты.
- Выполнение и отмену команд.
- Валидацию данных проекта.

Особенно важно тестировать пограничные случаи: нулевую длину стен, совпадающие точки,
отрицательные размеры и некорректные координаты.

### 20.2. Интеграционные проверки

Проверить корректную синхронизацию между состоянием проекта, визуализацией и инструментами.

Например, после удаления стены она должна исчезнуть из данных, сцены и списка выделенных
объектов.

### 20.3. Браузерные тесты

Использовать Playwright для проверки базовых сценариев:

- Запуск приложения.
- Создание проекта.
- Переключение инструментов.
- Сохранение.
- Повторное открытие проекта.
- Импорт и экспорт.
- Проверка отсутствия критических ошибок JavaScript.

Графические взаимодействия могут потребовать отдельной ручной проверки и стабильного
тестового окружения с WebGL.

### 20.4. Валидация и безопасность

При импорте JSON необходимо проверять структуру и ограничивать допустимый размер файла и
количество объектов.

Некорректные числовые значения, включая NaN и Infinity, не должны попадать в геометрический
движок.

Проектные данные не должны исполняться как JavaScript или использоваться для формирования
произвольного HTML.

Загрузка пользовательских GLB-файлов не входит в MVP и должна разрабатываться как отдельная
функция с проверкой формата, размеров и ресурсов.

## 22. План разработки

Создание проекта следует разделить на контролируемые этапы, каждый из которых заканчивается
работающей версией.

1. **Этап 0. Технический фундамент** *(начать здесь)* — создать проект Vite + React +
   TypeScript, подключить Three.js, настроить состояние, структуру папок и инструменты
   тестирования. Результат: запускаемое приложение с пустой 3D-сценой.
2. **Этап 1. Игровое пространство** *(MVP)* — реализовать участок, сетку, освещение,
   камеру, raycasting и переключение инструментов. Результат: пользователь может свободно
   осматривать участок.
3. **Этап 2. Строительная система** *(MVP)* — добавить создание стен, прямоугольных
   комнат, полов, выделение, удаление и изменение материалов. Результат: можно построить
   план простого дома.
4. **Этап 3. Мебель и территория** *(MVP)* — добавить небольшой каталог мебели, деревьев и
   прямых дорожек. Реализовать перемещение и поворот объектов. Результат: можно обустроить
   дом и участок.
5. **Этап 4. Сохранение и стабильность** *(MVP)* — добавить Undo/Redo, IndexedDB,
   экспорт/импорт JSON, валидацию и базовые тесты. Результат: готовая первая
   самостоятельная рабочая версия.
6. **Этап 5. Архитектурный редактор** *(после MVP)* — двери, окна, проёмы, соединения
   стен, несколько этажей, переключение видимости, плоские и двускатные крыши.
7. **Этап 6. Реалистичная графика** *(после MVP)* — качественные GLB-модели, текстуры,
   библиотека материалов, улучшенное освещение, интерьерные светильники и графические
   пресеты.
8. **Этап 7. Продвинутый редактор** *(расширение)* — сложные помещения, произвольные
   крыши, лестницы, редактирование рельефа, заборы, привязка к поверхностям и режим
   прогулки.
9. **Этап 8. Полноценный продукт** *(долгосрочно)* — облачное сохранение, аккаунты,
   галерея домов, обмен проектами, дополнительные участки и расширенная библиотека
   объектов.

Важно: после каждого этапа проект должен запускаться и сохранять работоспособность функций
предыдущих этапов.

Не допускается переходить к сложной графике, пока базовые инструменты строительства
нестабильны.

## 23. Критерии готовности первой версии

Первую версию можно считать готовой только после выполнения следующих требований.

- [ ] Приложение запускается в браузере — отсутствуют критические ошибки сборки и запуска.
- [ ] Отображается полноценная 3D-сцена — земля, сетка, освещение и тени.
- [ ] Камера свободно управляется — вращение, перемещение, приближение.
- [ ] Можно построить стены — две точки, предпросмотр, привязка к сетке.
- [ ] Можно создать комнату — четыре стены и пол за одну операцию.
- [ ] Работает выделение и удаление — объекты корректно исчезают из данных и сцены.
- [ ] Работает изменение материалов — минимальный набор отделки для стен и полов.
- [ ] Можно обустроить дом — несколько предметов с перемещением и поворотом.
- [ ] Можно обустроить участок — деревья и прямые дорожки.
- [ ] Работают Undo и Redo — для подтверждённых операций редактирования.
- [ ] Проект сохраняется — IndexedDB и экспорт/импорт JSON.
- [ ] Пройдены основные тесты — проверки геометрии, команд и сохранения.

Все критерии MVP должны быть отмечены и подтверждены тестами и проверкой приложения в
браузере, прежде чем переходить к Этапу 5.

## 24. Инструкции для агента разработки

Этот раздел определяет, как именно следует организовать работу с проектом.

**Правило № 1.** Не создавать всю игру в одном файле. Необходимо обеспечить разделение
интерфейса, данных и строительной логики.

**Правило № 2.** Не использовать 3D-сцену в качестве основного хранилища проекта.

**Правило № 3.** Не реализовывать новые функции за счёт разрушения существующих. После
значимых изменений выполнять сборку и тесты.

**Правило № 4.** Не добавлять недействующие кнопки, выдавая их за готовые возможности.
Каждая доступная функция должна выполнять действие.

**Правило № 5.** Не подменять требования скриншотами, концептами или статическими
HTML-макетами. Нужна настоящая интерактивная 3D-игра.

**Правило № 6.** Применять постепенную разработку. Сначала стабильная архитектура и
геометрия, затем дополнительные функции и визуальные улучшения.

**Правило № 7.** Документировать архитектурные изменения, особенно изменения модели данных
и системы сохранения.

**Правило № 8.** После каждого законченного этапа предоставлять отчёт о реализованных
функциях, результатах проверок и известных ограничениях.
